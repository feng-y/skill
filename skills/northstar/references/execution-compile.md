# 自主任务书（Autonomous Taskbook）

仅在 Stable Intent 之后使用。生成一本紧凑且权威的任务书，使 Executor 无需 Human 日常编排即可运行。

最终任务书必须严格按照下列顺序输出。保持每个章节的 authority 与证据职责彼此独立；细节可以随任务变化，但不得合并、重排，或把必需内容隐藏在其他章节中。

只编译会约束未来决策、执行步骤或完整 Goal 证明的信息。大段支持材料使用引用；全局事实只陈述一次，Task 内只写局部差异；省略已被替代的讨论和非活跃细节。

研究、选择或决策类工作也使用相同固定章节。在 Execution 中使用能产生证据的调查或决策，而不是实现 Task。每个结论都需要来源与日期，或可复现探针；伪造引用、未实际运行的“测量”和填充式结论均视为失败。对有边界的学习 Goal，一条证据充分的死路也可能满足目标。为有边界的学习工作声明预算，到达预算后停止，并交付证据支持最强的结论、反证和未解决替代方案；不要增加新的输出章节。

## 合同头（Contract Header）

简要声明六项内容：

- 本任务书是执行 source of truth；
- 唯一由 Human 拥有的 Goal；
- Why 以及完成后的世界；
- 本任务书需要关闭的声明交付；
- 要求冲突时的优先顺序；
- 哪些是硬规则，哪些是指导。

如果存在明确的执行停止预算，在这里声明；普通工作不要凭空增加预算。

## 1. 委托决策（Delegated Decisions）

将编译器拥有的默认值放在这里，并置于边界与执行之前，使 Human 能在 Handoff 前检查和纠正。

每个允许的委托默认值按以下形式输出：决策 → 默认值 → 依据 → 错误代价 → 检测或回滚路径。

如果没有此类选择，写 `None`；不要为了填充章节而虚构决策。

## 2. 边界与权限归属（Boundaries and Authority）

声明初始预期写入范围和所有受保护的禁止写入边界。证据表明关闭 Goal 必须扩大实现范围时，Executor 可以扩大范围，但已确认边界、受保护证明和 authority 必须保持不变；实质扩大范围的原因与影响必须在执行证据中明确说明。显式约束依赖新增或升级、权限、外部系统写入、破坏性操作及其他不可逆副作用。列出受保护测试、schema、验收脚本、CI、基线和其他判定器。指出容易顺手扩大的旁支工作和不可逆操作。

声明 Executor 在 Stable Intent 与受保护证明内部可以决定或调整什么。当某项操作超出已声明 authority 时，记录为等待 Human 明确授权的 blocker；高风险或不可逆操作始终采用该路由，除非已经明确预授权。当期望结果、验收要求或某项已确认边界重新变得不确定或将被改变时，返回 Intent Take。只有没有安全工作可继续时才 Block。

## 3. 当前现实与 Task 0（Current Reality and Task 0）

记录已有证据的事实与基线；标记未验证声明。

仓库或 runtime 已存在实现记录时复用；Northstar 不要求新增固定文件名或 artifact。

需要 Task 0 时，它必须在实质修改前运行。它绑定 repo、worktree 和 target，验证关键命令与判定器，发现空跑检查，并显露任务书执行假设与执行现实之间的重要不一致。证据可以修正事实、可行性、实现范围、计划和证明需要，但不得重新定义 Goal。优先把重要发现及其导致的路由变化保存在已有正常实现记录中；不存在此类记录时，保存在执行证据中。如果现实不同：

- 纠正不会改变期望结果、验收要求或已确认边界的明确任务书误读，然后继续；
- 稳定合同仍成立时重新规划；
- 仍有安全工作时，只暂停受影响分支；
- 没有安全工作时 Block，并给出准确解除条件；
- 期望结果、验收要求或某项已确认边界重新变得不确定或将被改变时，返回 Intent Take。

仍然有效的证据应直接复用；不要仪式化地重复发现过程。

## 4. 执行（Execution）

按真实依赖排列 Task。每个 Task 都声明可观察结果、成本最低且足够的局部证据，以及明确的局部 PASS 条件。代码修改的局部证明必须达到受影响单元测试或等价定向测试边界；如果该边界不可用，说明原因并使用最接近的直接探针。任务允许时，使 PASS 可由机器判断；否则使用显式证据和决策标准。只添加必要起点、依赖与写入所有权、硬约束、针对静默失败的反向验证，以及会使下游证据失效的上游条件。

把更广范围的编译、集成、replay 或端到端验证放在能够证明组合行为的最小边界：一组一致 Task 之后、依赖工作消费其结果之前，或分支重新汇合时。不要为每个 Task 重复昂贵的全系统验证；只有当某个 Task 改变系统级合同，或延后检查会显著增加恢复成本时，才提前运行。复用仍然有效的证据；只使那些其证明属性可能受到后续变化影响的证据失效并重跑。

简单工作保持线性。当真实分支、依赖、共享写入或汇合点会被线性列表掩盖时，阅读 [execution-graph.md](execution-graph.md)，并把最小依赖结构编译进普通 Task。

## 5. 执行规则（Execution Rules）

- 将 Task 视为当前可执行计划，而不是冻结范围；当证据变化时，可以在 Stable Intent、已确认边界、authority 与受保护证明内部增加、删除、拆分、合并或重排剩余 Task；
- 从所有可用安全工作继续推进，直到存在完整 Goal 证据、没有安全工作可继续，或明确的停止预算耗尽；分析完成、已有计划、局部 PASS、单一分支完成或部分交付都不是停止条件；
- 优先在仓库或 runtime 已有正常实现记录中保存重要决策、会改变证据的偏离、重新规划、范围扩大和 blocker；不要仅为 Northstar 创建例行进度或 blocker artifact；
- 执行恢复时，如果存在此类记录，行动前先阅读本任务书和该记录；只复用仍然有效的决定与证据，除非后续变化使既有证明失效，否则不要重复已完成工作；
- 发生阻塞时，保存 blocker、相关证据或尝试、解除条件，以及任何仍可继续的安全工作；
- 不得跳过测试、削弱断言、缩小被判定范围、用 mock 避开真实对象、吞掉失败、修改判定器，或接受更低基线，除非 Stable Intent 明确要求；
- 每次 retry 都必须改变假设或方法；立即停止已知错误路线；同一路线对同一验收条件失败三次后，必须重新规划、切换分支、回滚、`BLOCK` 或 `ESCALATE`；
- 回滚未授权回归，并如实报告失败；
- 遵守仓库分支、PR 和 pre-submit 规则。

## 6. 完成与验收（Completion and Acceptance）

要求完整 Goal 证据、边界与判定器保持不变、真实命令输出或可复现证明，以及如实残留项或 blocker。遵守所有声明的停止预算；如果预算耗尽仍未完成，报告准确的非 PASS 残留。局部 Task PASS 不等于完整 Goal PASS。

进行完整 Goal 验收时，在相关工作已经收敛且所有分支重新汇合后，运行声明交付所需的完整验证。复用仍然有效的局部与集成证据，但必须重跑所有其证明属性可能被后续变化破坏的判定器。

声明可见验收以及所有必需的独立验收边界。私有和独立验收遵循 [completion-trust.md](completion-trust.md)。如果所需 Acceptor 或验收环境不可用，结果上限为 `ready for independent acceptance`。

最终报告必须给出 `PASS`、`ready for independent acceptance` 或准确的非 PASS 路由；已交付结果；支持判断的证据；准确残留项或 blocker；以及下一条合法路由。不要用活动叙述替代证据。

Handoff 前验证：只有一个 Goal 和一个声明交付；至少一个 Task 或必需的 Task 0 可以立即开始；所有依赖均有现实依据；每个共享可变 surface 只有一个 owner；涉及 authority 的操作已被约束；每个分支都会重新汇合或具有显式终止路由；完整 Goal 证明仍然可达。不要编译 scheduler、lease 或固定 Agent 拓扑。

一本任务书必须在一次执行工作中关闭声明交付。一次执行工作指一本权威任务书和一个闭合交付；它不定义持久执行状态或 Agent 拓扑。runtime 支持时，Executor 可以委托、并行或使用依赖 Graph，但必须保持一个 Goal、清晰写入所有权和完整 Goal 验收。如果该交付无法在此合同下关闭，返回 Intent Take 缩小由 Human 拥有的交付；不要把 Goal 拆成多本任务书。
