# 自主任务书：把 Goal 编译成执行合同

只在 Goal 已经定准后使用。最终产物是一本紧凑、权威的任务书，Executor 拿到后无需 Human 日常指挥，也能独立完成本次交付。

任务书固定按下面六节输出。每节承担不同职责，不能合并、换序，也不能把必需内容藏到别处。细节多少随任务变化，只保留会影响后续决定、执行动作或完成证明的信息。

调研、选型和决策类工作也使用同一结构，只是“执行”中安排能产生证据的调查或判断，而不是代码 Task。每个结论都要有来源、日期或可复现探针。对有明确边界的学习 Goal，一条证据充分的死路也可能是有效结果；提前写清预算，到点后交付证据支持最充分的结论、反证和仍未解决的替代方案。

## 合同头

开头简要说清：

- 本任务书是本次执行的权威合同；
- 唯一、由 Human 决定的 Goal；
- 为什么做，以及做成后会有什么不同；
- 本次具体交付什么、拿什么证明；
- 要求冲突时按什么顺序取舍；
- 哪些是违反即不合格的硬规则，哪些只是可以结合现场调整的建议。

只有确实存在停止预算时才写。普通工作不要凭空增加时间盒或尝试次数。

## 1. 替 Human 决定

这里只记录 Northstar 在 Human 尚未明确选择时，替 Human 作出的可回退执行决定。它们必须出现在边界和执行之前，让 Human 在交付任务书前看见并纠正。

Northstar 只能决定不改变 Goal、验收要求和已确认边界的事项。每项写清：要决定什么 → 暂时怎么定 → 为什么这样定 → 猜错会有什么影响 → 如何发现并回退。

没有就写 `None`，不要为了填满章节虚构决定。

## 2. 边界与授权

先写预计会改哪些地方，再写明确不能改什么。证据证明完成 Goal 必须扩大实现范围时，Executor 可以扩大必要工作，但不能改变 Goal、已确认边界、验收要求或已有授权；范围明显扩大时，要在执行证据中写清原因和影响。

依赖新增或升级、权限变化、外部系统写入、破坏性操作和其他不可逆副作用，都要明确约束。列出不能被削弱的验收标准，例如测试、schema、验收脚本、CI 和基线。点名容易顺手做、但不属于本次 Goal 的事情。

写清 Executor 在 Goal 和边界内可以自行决定什么。超出已有授权的操作，记为等待 Human 决定的阻塞项；高风险或不可逆操作只有在已经明确授权时才能继续。Goal 或已确认边界必须改变时，回到 Intent Take。只有没有任何安全工作可以继续时，才返回 `Status: Blocked`。

## 3. 当前现实与 Task 0

记录已经有证据支持的事实和基线；没有验证的声明明确标出来。仓库或 runtime 已有正常的实现记录就直接复用，Northstar 不要求新建固定文件名或专用产物。

只有关键事实必须在执行环境中确认，而且错误假设会影响路线、边界或证明时，才设置 Task 0。它必须在实质修改前完成，并确认：

- 实际 repo、worktree 和 target；
- 关键命令和验收标准是否真的覆盖目标；
- 检查坏掉时是否会失败，是否存在空跑或假绿灯；
- 任务书和执行现实之间有没有重要差异。

新证据可以改变事实判断、实现范围、计划和验证方式，但不能改变 Goal。现实与任务书不一致时：

- 只是明确误读，而且纠正不会改变 Goal 或边界 → 纠正后继续；
- Goal 和边界仍成立 → 调整计划继续；
- 只有一个分支受影响 → 暂停该分支，继续其他安全工作；
- 没有安全工作 → `Status: Blocked`，写清解除条件；
- 必须改变 Goal 或已确认边界 → 回到 Intent Take。

产生证据时所依赖的版本、环境、对象和前提仍然成立，才可以直接复用；不要为了走流程重复发现。

## 4. 执行

按真实依赖排列 Task。每个 Task 至少写清：

- 完成后可以观察到什么；
- 成本最低且足够的局部证据是什么；
- 用什么条件明确判定局部 PASS 或 FAIL。

代码修改的局部证明必须到达受影响的单元测试或等价定向测试边界；该边界不可用时，说明原因，并使用最接近的直接探针。能由机器判断就写成机器可判定标准；不能时，写清需要看到的证据和判断方法。

更大范围的编译、集成、replay 或端到端验证，放在能够证明组合行为的最小位置：一组相关 Task 完成后、下游开始消费前，或并行分支汇合时。不要让每个 Task 重跑昂贵的全系统验证。后续变化只有可能破坏某项证据所证明的属性时，才让该证据失效并重跑。

简单任务保持线性。只有真实依赖、并行、共享写入或汇合点会被线性列表掩盖时，才阅读 [execution-graph.md](execution-graph.md)，把最小必要关系写进普通 Task。

## 5. 执行规则

- Task 是当前计划，不是冻结范围；证据变化时，可以在 Goal、边界、授权和验收要求内增加、删除、拆分、合并或重排剩余 Task；
- 只要还有安全工作，就继续推进，直到完整 Goal 已有证据、没有安全工作，或明确预算耗尽；分析完、计划写完、局部 PASS、一个分支完成或部分交付，都不是停止理由；
- 重要决定、会让既有证据失效的变化、重新规划、范围扩大和阻塞项，优先保存在仓库或 runtime 的正常实现记录中；不要只为 Northstar 新建例行进度文件；
- 恢复执行时，先读任务书和已有记录。只复用仍然成立的决定，以及产生前提仍然成立的证据；
- 分支阻塞时，保留阻塞项、已有尝试、解除条件和仍可继续的安全工作；
- 不得跳过测试、削弱断言、缩小验收范围、用 mock 绕开真实对象、吞掉失败、修改验收标准，或接受更低基线，除非 Goal 本身明确要求这种变化；
- 每次重试都必须改变假设或方法；已知错误路线立即停。同一路线对同一验收条件失败三次，必须重新规划、换分支、回滚、`BLOCK` 或 `ESCALATE`；
- 未授权回归必须回滚，并如实报告失败；
- 遵守仓库已有的分支、PR 和提交前规则。

## 6. 完成与验收

完整 Goal 必须有完整证据：边界没有被越过，验收标准没有被削弱，命令输出真实或证明可复现，并准确说明还有什么没完成或被什么卡住。局部 Task PASS 不等于完整 Goal PASS。

等相关工作收敛、并行分支重新汇合后，再运行本次交付需要的完整验证。产生前提仍然成立的局部和集成证据可以复用；后续变化可能破坏其证明的属性时，必须重跑。

写清明卷，以及是否需要暗卷或独立 Acceptor：

- **明卷**：Executor 在执行前可见的验收；
- **暗卷**：执行前冻结、与 Executor 隔离的验收；
- **独立 Acceptor**：没有参与实现，重新判断完整 Goal 是否通过。

具体机制遵循 [completion-trust.md](completion-trust.md)。必需的 Acceptor 或验收环境不可用时，结果最高只能是 `ready for independent acceptance`。

最终报告必须给出 `PASS`、`ready for independent acceptance`，或明确的非 PASS 路径，并说明：做成了什么、哪些证据支持判断、还有什么没完成或被什么卡住、下一步是什么。不要用活动清单代替证据。

交给 Executor 前再检查：只有一个 Goal 和一个明确交付；至少一个 Task 或必需的 Task 0 能立即开始；所有依赖有现实依据；共享写入有明确负责人；需要授权的操作已经约束；每个分支会汇合或有明确终止路径；完整 Goal 仍然可以被证明。不要编译 scheduler、lease 或固定 Agent 拓扑。

一本任务书必须在一次执行工作中完成并证明本次交付。runtime 支持时，Executor 可以委托、并行或使用 Graph，但必须保持一个 Goal、明确的共享写入责任和完整 Goal 验收。如果做不到，回到 Intent Take 缩小本次 Goal；不要把一个 Goal 拆成多本任务书。
