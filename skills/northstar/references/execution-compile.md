# 自主任务书：把稳定意图写成执行合同

只在 Stable Intent 已经成立后使用。最终产物是一本紧凑、权威的任务书，Executor 拿到后无需 Human 日常指挥，也能独立推进。

任务书必须严格按下面的顺序输出。每一节负责不同的权限和证据问题；细节可以随任务增减，但不能合并、换序，也不能把必需内容藏到别的章节里。

只写会影响后续决策、执行动作或完整 Goal 证明的信息。大段材料用引用；全局事实只写一次，Task 内只补局部差异；已经被替代的讨论和当前用不到的细节全部删掉。

调研、选型和决策类工作也使用同一套六节结构，只是 Execution 中写“会产出证据的调查或决策”，而不是实现 Task。每个结论都必须有来源和日期，或有可复现探针；伪造引用、没有实际运行的“测量”和凑数结论都算失败。对有明确边界的学习 Goal，一条证据充分的死路也可能是有效结果。提前写清预算，到点就停，交付证据最强的结论、反证和仍未解决的替代方案；不要另加输出章节。

## 合同头（Contract Header）

开头简要说清六件事：

- 本任务书是本次执行的权威合同；
- 唯一且由 Human 拥有的 Goal；
- 为什么做，以及做成后会有什么不同；
- 本任务书这一次必须完成并证明的交付；
- 要求冲突时按什么顺序取舍；
- 哪些是必须遵守的硬规则，哪些只是可以调整的指导。

只有确实存在执行停止预算时才写；普通工作不要凭空加时间盒或尝试次数。

## 1. 委托决策（Delegated Decisions）

Northstar 代为选择、但 Human 尚未确认的默认值，全部放在这里，并且必须早于边界和执行。这样 Human 能在 Handoff 前看见并纠正。

每项按这个顺序写：要决定什么 → 暂用什么默认值 → 依据 → 猜错的代价 → 如何发现或回滚。

没有就写 `None`，不要为了填满章节虚构决策。

## 2. 边界与权限（Boundaries and Authority）

先写预期写入范围，再写明确禁止触碰的范围。证据证明“要完成并证明 Goal 就必须扩大实现范围”时，Executor 可以扩大，但不能改变已确认边界、不可削弱的证明要求或权限分配；范围实质扩大时，必须在执行证据中写清原因和影响。

依赖新增或升级、权限变更、外部系统写入、破坏性操作及其他不可逆副作用，都要明确约束。列出不能被削弱的测试、schema、验收脚本、CI、基线和其他判定器。点名看起来顺手、实际不属于本次 Goal 的旁支工作，以及所有不可逆操作。

写清 Executor 在 Stable Intent 和不可削弱的证明要求内可以自行决定或调整什么。超出已声明权限的操作，记为等待 Human 明确授权的阻塞项；高风险或不可逆操作默认走这条路，除非已经预授权。期望结果、验收要求或已确认边界重新不稳定，或者继续推进必须改变它们时，回到 Intent Take。只有没有任何安全工作可继续时，才返回 `Status: Blocked`。

## 3. 当前现实与 Task 0（Current Reality and Task 0）

记录已经有证据支持的事实和基线；没有验证的声明明确标出来。

仓库或 runtime 已有正常的实现记录就直接复用；Northstar 不要求新建固定文件名或专用产物。

需要 Task 0 时，它必须在实质修改之前执行。Task 0 绑定真实 repo、worktree 和 target，验证关键命令与判定器，识别空跑检查，并暴露任务书假设和执行现实之间的重要差异。证据可以修正事实、可行性、实现范围、计划、证明需要和证明方式，但不能重新定义 Goal。重要发现及其导致的路由变化，优先写进已有实现记录；没有时写进执行证据。

现实与任务书假设不一致时：

- 如果只是任务书被明确误读，而且纠正不会改变结果、验收要求或已确认边界，纠正后继续；
- 稳定合同仍成立，重新规划；
- 还有安全工作，只暂停受影响分支；
- 没有安全工作，返回 `Status: Blocked`，并写清解除条件；
- 结果、验收要求或已确认边界重新不稳定或必须改变，回到 Intent Take。

仍然有效的证据直接复用，不要为了走流程而重复发现。

## 4. 执行（Execution）

按真实依赖排列 Task。每个 Task 至少写清三件事：完成后能观察到什么、成本最低且足够的局部证据是什么、什么条件下局部 PASS。

代码修改的局部证明必须到达受影响的单元测试或等价定向测试边界；如果这个边界不可用，说明原因，并使用最接近的直接探针。能机器判断就给机器判据；不能时，给明确证据和决策标准。只补充真正影响执行的起点、依赖、写入所有权、硬约束、针对静默失败的反向验证，以及哪些上游变化会让当前证据失效。

更大范围的编译、集成、replay 或端到端验证，放在能证明组合行为的最小位置：一组彼此连贯的 Task 之后、下游消费结果之前，或并行分支重新汇合时。不要给每个 Task 重跑昂贵的全系统验证；只有 Task 改变了系统级合同，或晚查会显著抬高恢复成本时，才提前验证。仍然有效的证据继续用；只有后续变化可能破坏其证明属性时，才让它失效并重跑。

简单任务保持线性。真实分支、依赖、共享写入或汇合点会被线性列表掩盖时，阅读 [execution-graph.md](execution-graph.md)，把最小依赖关系写进普通 Task。

## 5. 执行规则（Execution Rules）

- Task 是当前可执行计划，不是冻结范围。证据变化时，可以在 Stable Intent、已确认边界、权限和不可削弱的证明要求内增加、删除、拆分、合并或重排剩余 Task；
- 只要还有安全工作，就继续推进，直到完整 Goal 已有证据、没有安全工作，或明确停止预算耗尽。分析完、计划写完、局部 PASS、一个分支完成或部分交付，都不是停止理由；
- 重要决策、会改变证据的偏离、重新规划、范围扩大和阻塞项，优先保存在仓库或 runtime 的正常实现记录中；不要只为 Northstar 新建例行进度文件或专用阻塞文件；
- 恢复执行时，如果存在这类记录，行动前先读任务书和记录。只复用仍然有效的决定与证据；后续变化没有使证明失效，就不要重复已经完成的工作；
- 发生阻塞时，保留阻塞项、相关证据和尝试、解除条件，以及仍可继续的安全工作；
- 不得跳过测试、削弱断言、缩小判定范围、用 mock 绕开真实对象、吞掉失败、修改判定器或接受更低基线，除非 Stable Intent 明确要求；
- 每次重试都必须改变假设或方法；已知错误路线立即停。同一路线对同一验收条件失败三次，必须重新规划、换分支、回滚、`BLOCK` 或 `ESCALATE`；
- 未授权回归必须回滚，并如实报告失败；
- 遵守仓库已有的分支、PR 和提交前规则。

## 6. 完成与验收（Completion and Acceptance）

完成必须有完整 Goal 证据，已确认边界保持不变、判定器未被削弱，命令输出真实或证明可复现，残留项和阻塞如实。存在停止预算时必须遵守；预算耗尽仍未完成，就报告准确的非 PASS 残留。局部 Task PASS 不等于完整 Goal PASS。

做完整 Goal 验收时，等相关工作收敛、并行分支重新汇合，再运行本次交付所需的完整验证。仍然有效的局部和集成证据可以复用；后续变化可能破坏了某个判定器所证明的属性，就必须重跑它。

写清可见验收，以及是否需要独立 Acceptor 或独立验收边界。私有和独立验收遵循 [completion-trust.md](completion-trust.md)。所需 Acceptor 或验收环境不可用时，结果上限是 `ready for independent acceptance`。

最终报告必须给出 `PASS`、`ready for independent acceptance` 或准确的非 PASS 路由，并说明：交付了什么、哪些证据支持判断、还剩什么或卡在哪里、下一条合法路线是什么。不要用“做了哪些活动”代替证据。

Handoff 前再检查：只有一个 Goal 和一个明确交付；至少一个 Task 或必需的 Task 0 能立即开始；所有依赖都有现实依据；每个共享写入点只有一个负责人；涉及权限的操作都已约束；每个分支都会汇合或有明确终止路由；完整 Goal 仍然可以被证明。不要编译 scheduler、lease 或固定 Agent 拓扑。

一本任务书必须在一次执行工作中完成并证明本次交付。“一次执行工作”只表示一本权威任务书和一个完成且已有证明的交付，不规定持久执行状态或 Agent 拓扑。runtime 支持时，Executor 可以委托、并行或使用依赖 Graph，但必须保持一个 Goal、明确写入所有权和完整 Goal 验收。如果做不到，回到 Intent Take 缩小 Human 本次要的交付；不要把一个 Goal 拆成多本任务书。
