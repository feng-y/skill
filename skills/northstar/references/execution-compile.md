# 当简单 Taskbook 不够

只在 Goal 已经定准，但任务很长、需要几种不同判断、明确先后关系、较强验收或跨会话继续时读取。内容仍按 `SKILL.md` 的 Compile 判断筛选；这里只展开复杂执行时怎么组织。

## 写判断，不抄调研

repo/runtime 能可靠重算的事实默认不写；不写会让 Executor 误删、误留、越界或漏验收的事实才写。Research 越深，Taskbook 应该越像少量稳定判断，而不是事实汇编。

当前 workspace 中已经与 Goal 对齐的修改就是起点：不要求重做，也不能因为已有 diff 就缩小 Goal；“已经改了”本身也不是正确性证据。

基线只有在它真的帮助判断有没有漏项，或区分“原来就坏”与“这次改坏”时才值得写。命令、target、参数必须来自真实环境，不能编造。

## 只在判断不同的地方拆工作

一批对象如果都能用同一个判断处理，就作为一项工作，让 Executor 在约定范围内扫全；不要按文件、函数或当前发现的实例拆。只有局部要达到的结果、判断规则、真实依赖或验收要求不同，才值得拆开。

如果缺一个事实就连第一项安全修改都不能开始，把这个事实放在最前面查清；不要因此再开一轮大 Research。

通常不需要画执行图。只有关系会改变下一步选择时才写，例如：B 必须等 A 的结果、两项可以并行、几项会改同一个权威文件、或者几项必须合起来验收。只写当前 reality 已经证明的关系；必须等执行后才知道的后续工作，等它真的出现再加。一个分支受阻，不应冻结与它无关的工作。

## 写清怎么证明，不规定怎么调试

Taskbook 只写 Goal 完成后必须有什么证据。build/test/replay 的执行顺序、每改一步就测一次等定位问题的方法，默认由 Executor 自己决定。

如果 Taskbook 把某个基线当作后续判断前提，Executor 在第一次依赖它之前重新取得；结果不一致时，只重算依赖这个前提的工作和证据，其他仍有效部分继续复用。

Research 中发现一个候选对象，不等于它必须 `0-hit / 0-count`。只有已经证明它必须消失，而且“归零”本身就是 Goal 的一部分时，才这样验收。

如果存在具体“实现其实错了但仍可能显示 PASS”的风险，再读 [verification-trust.md](verification-trust.md)。否则不要增加额外判卷机制。

失败也要诚实：可信基线从绿变红时先恢复或准确报告；同一路线反复失败且没有新证据时，换有依据的策略、先做独立工作或报告 blocker。禁止通过 skip/todo、放松断言、删活体测试、mock 掉目标、吞失败或 `|| true` 制造成功。

## 让长任务能接着做

较长 autonomous run 使用现有 `implement-notes` 记录进展、关键决定和证据、阻塞原因、下一次从哪里继续。新 session 先读它，只重做前提已经变化或证据已经失效的部分；不要另造第二份 Taskbook、持久执行图或 manager state。
