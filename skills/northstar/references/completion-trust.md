# 完成可信度（Completion Trust）

当任务可能在没有证明期望结果的情况下看似完成时使用。

## 证明规则

- **直接证明目标属性。** 当 build、lint、coverage 或活动记录不能证明 Goal 时，它们不能作为替代。
- **证明判定器能够失败。** 当关键检查可能空跑或误判 PASS 时，制造一个受控且局部的失败，确认失败信号出现，恢复状态，再运行正常证明。
- **冻结判定器。** 除非 Stable Intent 明确要求改变且仍保持等价可信度，否则 Executor 不得削弱断言、缩小被判定范围、用 mock 替代真实对象、降低阈值、绕过失败传播、跳过测试或修改验收标准。常见的低成本伪合规包括 `.skip`、删除测试，以及用 `|| true` 吞掉失败；这些是假完成，不是聪明捷径。
- **保护基线。** 任何低于已有证据基线的结果，即使成本更低，也属于回归，而不是完成，除非得到明确授权。

为每个 Task 附上局部证明。局部 PASS 可以解锁依赖工作，但不能关闭完整 Goal。当上游变化影响了下游证据所证明的属性时，该证据失效。

## 私有验收

Handoff 前，根据公开 Goal、边界和完成属性推导并预留一组小型私有验收，通常为两到三个检查，并在执行前冻结。私有检查可以使用未列出的样本或不同观察路径，但绝不能加入隐藏要求。

将该检查集保留在 Executor 可见任务书之外；runtime 支持上下文隔离时，放在编译器、Acceptor 上下文或其他 Executor 无法访问的位置。如果 runtime 无法对 Executor 隐藏它们，就不要声称拥有私有证明：要么在隔离上下文中执行，要么将其视为可见检查，并在仍需要独立性时要求其他受保护或独立证明。

执行结束后，先重新运行可见判定器，再运行预留检查，之后才能给出最终 PASS。私有检查失败表示公开合同仍有准确残留项，而不是新增要求。

## 独立验收

只有在未实质参与实现，并直接依据权威任务书、验收环境和受保护判定器进行判断，而不是接受 Executor 结论时，Acceptor 才具备独立性。模型或服务提供方是否相同，既不能单独证明独立，也不能单独否定独立。

当 Executor 自证容易被钻空子、不完整或不足以形成可信判断时，使用独立 Acceptor；这也包括本应私有的检查已对 Executor 可见，并且没有其他受保护判定器能够关闭 Goal 的情况。在执行前绑定独立 Acceptor，或预留独立验收边界。Executor 的实现说明与证据只是输入，不是最终判断。

如果所需 Acceptor 或验收环境不可用，返回一份自包含验收交接，其中包含：权威任务书、Executor 结果与证据、可见验收、预留验收检查及其可见性、受保护判定器与基线，以及所需最终报告——`PASS` 或准确残留项。最高诚实结果仍是 `ready for independent acceptance`，而不是 `PASS`。

被破坏、伪造、跳过或已过期的证明，都等同于未满足。非 PASS 必须路由到新证据、实质不同的计划、如实阻塞项或相应 Human 边界；绝不能被改写成完成。
