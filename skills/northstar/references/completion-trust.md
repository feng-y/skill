# 完成可信度：别让假完成过关

当任务可能“看起来做完了”，却没有真正证明 Human 要的结果时，使用本文件。

## 四条证明规则

- **直接证明目标属性。** build、lint、coverage 或活动记录只有在确实证明 Goal 时才有用；否则都不能代替结果证明。
- **先证明判定器真的会失败。** 关键检查可能空跑或假通过时，制造一次受控且局部的失败，确认失败信号真的出现，恢复状态，再运行正常证明。
- **判卷标准不能偷改。** 除非 Stable Intent 明确要求改变，而且仍保留等价可信度，否则 Executor 不得削弱断言、缩小判定范围、用 mock 替代真实对象、降低阈值、绕过失败传播、跳过测试或修改验收标准。`.skip`、删测试、用 `|| true` 吞失败，都是假完成，不是聪明捷径。
- **基线不能倒退。** 任何低于已有证据基线的结果，即使成本更低，也属于回归，不属于完成，除非得到明确授权。

每个 Task 都要有局部证明。局部 PASS 可以解锁下游工作，但不能证明完整 Goal 已完成。上游变化影响了下游证据原本证明的属性，下游证据就失效。

## 私有验收：执行者看不到的抽查

Handoff 前，根据公开 Goal、边界和完成属性，推导并预留一小组私有检查，通常两到三条，并在执行前冻结。检查可以使用任务书没有列出的样本，或换一条观察路径，但不能偷偷增加新要求。

这组检查不进入 Executor 可见的任务书。runtime 能隔离上下文时，把它放在编译器、Acceptor 上下文或其他 Executor 无法访问的位置。runtime 无法隐藏时，就不能声称它是私有证明：要么换到隔离上下文执行，要么把它当作可见检查，并在仍需独立性时增加其他受保护或独立证明。

执行结束后，先重跑可见判定器，再跑预留检查，之后才能给最终 PASS。私有检查失败，表示公开合同仍有准确残留项，不是突然增加了新要求。

## 独立验收：由没参与实现的人重新判

Acceptor 只有在未实质参与实现，并直接依据权威任务书、验收环境和受保护判定器重新判断，而不是接受 Executor 自己的结论时，才算独立。模型或服务提供方相同与否，既不能单独证明独立，也不能单独否定独立。

Executor 自证可能被钻空子、证据不完整或不足以形成可信判断时，使用独立 Acceptor。本应私有的检查已经对 Executor 可见、又没有其他受保护判定器能证明 Goal 完成，也走这条路。独立 Acceptor 或独立验收边界必须在执行前绑定或预留。Executor 的实现说明和证据只是输入，不是最终判定。

所需 Acceptor 或验收环境不可用时，返回一份自包含验收交接：权威任务书、Executor 结果与证据、可见验收、预留检查及其可见性、受保护判定器与基线，以及最终报告要求——`PASS` 或准确残留项。最高诚实结果仍是 `ready for independent acceptance`，不能写成 `PASS`。

被破坏、伪造、跳过或已经失效的证明，都等于没有满足。非 PASS 必须走向新证据、实质不同的计划、如实阻塞，或相应 Human 边界；绝不能改写成完成。
