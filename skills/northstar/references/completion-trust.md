# 完成可信度：防止假完成

当任务可能“看起来做完了”，却没有真正证明 Goal 时，使用本文件。

## 四条证明规则

- **直接证明 Goal 要求的属性。** build、lint、coverage 或活动记录，只有在确实证明目标属性时才有用；否则不能代替结果证明。
- **反向验证。** 关键检查可能空跑或出现假绿灯时，制造一次受控且局部的失败，确认检查确实变红；恢复状态后，再运行正常证明。
- **验收标准不能偷改。** Executor 不得通过削弱断言、缩小覆盖范围、用 mock 替代真实对象、降低阈值、吞掉失败、跳过测试或修改验收条件来获得通过，除非 Goal 本身明确要求改变，而且仍保留同等可信度。
- **基线不能倒退。** 低于已有可信基线的结果属于回归，不属于完成，除非 Human 已经明确接受。

每个 Task 都要有局部证明。局部 PASS 可以解锁下游工作，但不能证明完整 Goal 已完成。上游变化影响了某份证据原本证明的属性，这份证据就失效。

## 明卷与暗卷

- **明卷**：Executor 在执行前能够看到的验收内容。它用于指导实现和自测。
- **暗卷**：根据公开 Goal、边界和完成条件，在执行前推导并冻结，且与 Executor 隔离的验收内容。它用于检查实现是否只迎合了明卷，或是否存在假完成。

只有明卷可能假通过、容易被针对，或不足以证明完整 Goal 时，才需要暗卷。暗卷通常两到三条，可以使用任务书没有列出的样本或不同观察路径，但不能增加隐藏要求。

暗卷不能进入 Executor 可见的任务书。runtime 能隔离上下文时，把它保留在 Northstar、Acceptor 或其他 Executor 无法访问的位置。runtime 无法隐藏时，就不能声称拥有暗卷：要么换到隔离上下文执行，要么把这些检查当作明卷，并补充其他可信或独立的验收。

执行结束后，先重跑明卷，再运行暗卷。暗卷失败，说明公开 Goal 仍有具体事项没有完成，不是临时增加了新要求。

## 独立验收

当 Executor 自己提供的证据可能被钻空子、不完整，或者单靠这些证据不能证明完整 Goal 时，由独立 Acceptor 验收。

Acceptor 必须没有实质参与实现，并直接根据任务书、验收环境、明卷、暗卷和受保护的验收标准重新判断。模型或服务提供方是否相同，不能单独证明或否定独立性。Executor 的实现说明和证据只是输入，不是最终判断。

本应隔离的暗卷已经暴露给 Executor，而且没有其他可信验收能够证明完整 Goal 时，也必须走独立验收。独立 Acceptor 或独立验收边界要在执行前绑定或预留。

所需 Acceptor 或验收环境不可用时，返回一份自包含交接：任务书、Executor 的结果和证据、明卷、暗卷及其可见性、受保护的验收标准和基线，以及最终需要给出的 `PASS` 或仍未完成的事项。此时最高只能声明 `ready for independent acceptance`。

伪造、跳过、过期或已经失去可信性的证明，都等于没有证明。非 PASS 必须转向新证据、实质不同的计划、如实阻塞，或需要 Human 决定的边界；绝不能改写成完成。
