# 战略设计

只在当前目标结构不清、已有架构设计不足或互相冲突时读取。本文件帮助 AE 做战略设计；仓库中的架构文档只是战略设计稳定结论的持久化形式，不是第二套流程，也不是完整蓝图。

Strategic Design 回答系统长期应该是什么；Tactical Evolution 只回答当前现实下值得先推进哪一刀。当前迁移成本、实现难度、局部 pressure 或已有 patch 可以影响战术选择，但不能把一个较便宜、较容易或已经存在的结构重新定义成 Target Architecture。只有新的领域事实、长期约束、权威或已验证现实推翻了战略前提时，才重算受影响的战略设计。

## 要回答什么

战略设计只回答会长期影响结构的几个问题：

- 这个 repo / 系统为什么存在、在更大系统中承担什么核心职责，当前范围在整体中预期扮演什么角色，哪些能力或权威明确属于其他 owner；
- 系统的主要能力是什么，各自拥有哪类知识、状态、行为、权威、生命周期和主要验证；
- 哪些长期变化应在同一个能力内被吸收，哪些差异只是能力内部 variation，哪些边界因为独立语义、权威或生命周期必须长期分开；
- 主要能力之间什么关系应长期稳定，依赖应往哪走；
- 什么语义真正通用，什么差异应保持特化；
- 调用方必须知道什么，哪些复杂性应被边界隐藏；
- 主要能力内部什么语义稳定，具体实现的变化应在哪个边界被吸收，内部依赖应往哪走；
- 哪些结构判断仍缺决定性证据，应保持未决。

高内聚低耦合不是独立评分项，也不是最后才看的副产品，而是检验长期能力划分是否正确的结构结果：同一能力因同一种长期语义或变化原因一起变化的知识、状态、行为、权威、生命周期和验证应尽量在 owner 内闭合；不同能力之间只交换稳定、必要的信息。若只能在当前模块内部得到“更内聚”的结构，但仍无法解释它为什么应作为长期能力存在，战略设计还没有完成。

## 用什么证据

先找会改变当前范围战略方向的 repo / system identity、architecture intent 和现实证据，不默认文件名，也不把某一份材料当 oracle。README、架构来源、领域文档、ADR、公开入口、真实 consumer、代码、配置、测试、运行时和修改历史都只能按各自证明力提供 Evidence；需要时沿真实 workflow 核对这个系统实际承担什么核心职责、在更大系统中扮演什么角色、当前范围由谁消费、哪些 authority/lifecycle 已经独立存在。只恢复足以判断当前范围预期角色的 repo-level 方向，不为此展开全 repo inventory。

已有权威来源仍按自身证明力和前提是否成立使用：明确的责任、依赖、分层、跨边界入口或机械检查若前提仍成立，就约束候选结构；前提失效时，不再把对应结论当作当前约束，并把原权威来源的演进纳入战略设计结论。外部项目、文章和通用架构模式只用于比较和挑战，不替代当前 repo 的权威，也不因为外部系统采用某个固定层序就机械套用到当前能力。领域文档说明业务语言和概念；ADR 说明某次重要取舍及当时理由；代码、配置、测试和运行时说明当前现实；修改历史说明哪里以及怎样发生变化；工程摩擦说明当前结构在哪些地方难以理解、切分、修改或验证。它只有在能追溯到长期能力、责任、依赖、抽象或权威边界时才是架构证据；需求本身过大、测试环境笨重、一次性实现困难都可能只是局部问题。任何一类材料都不能单独代替战略设计。

不要把当前目录树、类关系、模块名或已有实现直接抬升成 repo identity、能力划分或目标结构，也不要因为某份旧架构文档存在就停止判断。已有设计与现实冲突时，检查其前提是否仍成立。

## 怎样形成目标结构

从当前问题覆盖的最小范围开始，但先恢复足以判断这个范围在 repo / system 中**预期应该承担什么**的战略锚点；范围仍由长期责任、权威和变化边界决定，不由当前代码边界决定，也不因为需要 repo identity 就设计整个 repo。

不要把当前 module / class / package 当作待优化的固定候选集合。依据当前最可信的 repo identity、领域语义和已确认的长期变化，重新判断主要能力应该怎样划分：哪些知识、状态、行为、权威、生命周期和验证会因同一种长期语义或变化原因一起变化，应由同一个 owner 吸收；哪些差异只是能力内部实现或配置变化，哪些语义、权威、生命周期、性能架构或部署边界真正独立，值得形成长期结构。一个长期变化若总要跨多个当前 owner 重组同一份私有知识，先问“这类变化的 natural home 应在哪里”，而不是先优化这些 owner 之间的连线。

能力与责任边界先成立，再设计依赖方向、通用/特化和信息隐藏。单向依赖是重要结构约束，但不能替代正确的 capability decomposition：一个能力的知识和变化即使沿着漂亮的单向层级散落在多个 owner，仍然可能是错误结构。确定能力之间的边界，也不等于能力内部的战略设计已经完成；若能力内部仍有长期责任、依赖或抽象问题，继续确定内部稳定语义、具体实现的隔离边界和允许依赖，使稳定语义不依赖具体实现。

单向依赖不等于预设固定层数或层名。只有当前 repo 自己已有仍有效的分层或依赖约束时，才按这些约束检查候选；没有这类权威或稳定内部角色时，不为形式整齐套用外部层序。长期依赖边界仍优先通过目录、模块、包、构建或工具机械约束。运行时调用顺序只说明现实行为，不代替代码依赖设计。

候选结构至少要经得住四个问题：

1. **理解**：理解一个主要能力，是否必须跨很多不相干责任重建知识？
2. **修改**：同类变化是否会穿过本不该参与的模块？
3. **切分**：一个合理范围的业务需求能否主要沿责任边界拆开，而不是按文件或技术层硬切？先排除需求本身范围失控或责任归属未决。
4. **验证**：主要行为能否从对应责任附近获得可靠证据，而不是绕过边界拼装内部细节？先区分架构边界问题与测试基础设施、外部依赖或环境成本。

能力内部存在这类长期结构复杂性时，同样用这四个问题检查内部结构：稳定语义不依赖具体实现，同类变化能在明确边界被吸收；如果 repo 自己已有仍有效的分层或依赖约束，再检查候选是否满足它。

若多个候选都经得住这些问题，再比较它们对后续变化的传播：优先让同类持续或已明确的未来变化少跨责任、权威、依赖和验证面，而不是选择当前改动更大或更整洁的结构。只有边界真实更清楚时这种局部性才成立；不能吞并独立权威或生命周期，也不能复制事实或隐藏真实跨边界语义。

这些问题用于挑战设计，不意味着追求单模块、单测试或最少文件。真实独立的权威、生命周期和领域语义可以合理地跨边界。

Target Architecture 稳定后，再由主 Skill 根据当前 reality 选择 Tactical Evolution。某个 gap 当前不值得做、风险过高或只能安全推进一部分，只改变“现在做什么”，不改变“长期应该怎样”；如果战术执行产生新 Evidence 推翻战略前提，再只重算受影响的战略判断。

## 持久化战略设计

当战略设计形成了跨变化仍会复用的稳定结论，才把它沉淀到 repo 的权威架构来源。内容应短、局部、可修订，只记录责任、边界、依赖、通用/特化、重要不变量和仍未决的结构问题。不要写目录清单、实现步骤、一次性迁移方案或当前代码说明。

已有权威架构来源优先原位更新，不建平行 SOT。repo 没有架构来源时，也不要因为一次 AE run 自动创建全量 `ARCHITECTURE.md`；只有结论已经稳定、未来确实会复用且用户授权时，才建立最小来源。
