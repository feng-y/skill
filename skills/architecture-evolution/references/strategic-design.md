# 战略设计

只在当前目标结构不清、已有架构设计不足或互相冲突时读取。本文件帮助 AE 做战略设计；仓库中的架构文档只是战略设计稳定结论的持久化形式，不是第二套流程，也不是完整蓝图。

## 要回答什么

战略设计只回答会长期影响结构的几个问题：

- 系统的主要能力是什么，各自拥有哪类知识、状态、权威和生命周期；
- 模块之间什么关系应长期稳定，依赖应往哪走；
- 什么语义真正通用，什么差异应保持特化；
- 调用方必须知道什么，哪些复杂性应被边界隐藏；
- 哪些结构判断仍缺决定性证据，应保持未决。

高内聚低耦合不是独立评分项，而是这些判断成立后的结果：同一责任需要的知识、状态和验证尽量闭合；跨责任只交换稳定、必要的信息。

## 用什么证据

先找仓库已经认可的架构来源，不默认文件名。区分解释设计的材料与约束候选结构的 repo contract：固定分层、禁止依赖、跨域入口和机械检查若仍适用，就是设计约束；只有其前提已经失效，才重新设计并更新原权威来源。找到直接涉及当前范围的权威来源后，核对其中全部适用约束，而不是只摘取支持当前结构的一条；目标结构要逐条吸收，或明确哪条因前提失效需要演进。其他材料各按自己的证明力使用：领域文档说明业务语言和概念；ADR 说明某次重要取舍及当时理由；代码、配置、测试和运行时说明当前现实；修改历史说明哪里以及怎样发生变化；工程摩擦说明当前结构在哪些地方难以理解、切分、修改或验证。它只有在能追溯到责任、依赖、抽象或权威边界时才是架构证据；需求本身过大、测试环境笨重、一次性实现困难都可能只是局部问题。任何一类材料都不能单独代替战略设计。

不要把当前目录树、类关系或已有实现直接抬升成目标结构，也不要因为某份旧架构文档存在就停止判断。已有设计与现实冲突时，检查其前提是否仍成立。

## 怎样形成目标结构

从当前问题覆盖的最小范围开始，不设计整个 repo。用户点名的文件、类或模块只是搜索锚点；从叶子症状向外找到能拥有这类长期变化并解释摩擦的最小稳定责任范围，以它作为设计中心。

用两张逻辑图完成设计。责任图的节点按能力与变化边界命名，说明稳定 owner 之间的权威、依赖和产品族通用/特化，再把当前类映射到 owner；当前类清单本身不是责任图，识别出 provider capability 也不等于要求新增 `Provider` 类。源码依赖图进入每个相关 owner，说明长期知识、状态与生命周期如何由单向依赖闭合；每个稳定 owner 独立对应，共享 seam 必须归属某个 owner，不能把多个 owner 合并进一条层序。仓库已有固定层序时，逐个 owner 展示使用的层、合理省略的层、允许的前向 import、Providers 入口和机械约束；没有这种权威或稳定内部角色时，不为形式整齐制造分层。配置、装载、执行和返回结果的运行顺序不等于源码依赖图。

候选结构至少要经得住四个问题：

1. **理解**：理解一个主要能力，是否必须跨很多不相干责任重建知识？
2. **修改**：同类变化是否会穿过本不该参与的模块？
3. **切分**：一个合理范围的业务需求能否主要沿责任边界拆开，而不是按文件或技术层硬切？先排除需求本身范围失控或 责任归属未决。
4. **验证**：主要行为能否从对应责任附近获得可靠证据，而不是绕过边界拼装内部细节？先区分架构边界问题与测试基础设施、外部依赖或环境成本。

若多个候选都经得住这些问题，再比较它们对后续变化的传播：优先让同类持续或已明确的未来变化少跨责任、权威、依赖和验证面，而不是选择当前改动更大或更整洁的结构。只有边界真实更清楚时这种局部性才成立；不能吞并独立权威或生命周期，也不能复制事实或隐藏真实跨边界语义。

这些问题用于挑战设计，不意味着追求单模块、单测试或最少文件。真实独立的权威、生命周期和领域语义可以合理地跨边界。

## 持久化战略设计

当战略设计形成了跨变化仍会复用的稳定结论，才把它沉淀到 repo 的权威架构来源。内容应短、局部、可修订，只记录责任、边界、依赖、通用/特化、重要不变量和仍未决的结构问题。不要写目录清单、实现步骤、一次性迁移方案或当前代码说明。

已有权威架构来源优先原位更新，不建平行 SOT。repo 没有架构来源时，也不要因为一次 AE run 自动创建全量 `ARCHITECTURE.md`；只有结论已经稳定、未来确实会复用且用户授权时，才建立最小来源。
