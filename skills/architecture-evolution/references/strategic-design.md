# 战略设计

只在当前目标结构不清、已有架构设计不足或互相冲突时读取。本文件帮助 AE 做战略设计；仓库中的架构文档只是战略设计稳定结论的持久化形式，不是第二套流程，也不是完整蓝图。

## 要回答什么

战略设计只回答会长期影响结构的几个问题：

- 系统的主要能力是什么，各自拥有哪类知识、状态、权威和生命周期；
- 主要能力之间什么关系应长期稳定，依赖应往哪走；
- 什么语义真正通用，什么差异应保持特化；
- 调用方必须知道什么，哪些复杂性应被边界隐藏；
- 主要能力内部什么语义稳定，具体实现的变化应在哪个边界被吸收，内部依赖应往哪走；
- 哪些结构判断仍缺决定性证据，应保持未决。

高内聚低耦合不是独立评分项，而是这些判断成立后的结果：同一责任需要的知识、状态和验证尽量闭合；跨责任只交换稳定、必要的信息。确定能力之间的边界，不等于能力内部的战略设计已经完成。

## 用什么证据

先找仓库已经认可的架构来源，不默认文件名。范围收敛前，有界检查直接涉及当前能力或产品族，或声明适用于整个 repo / 一类能力的架构约束；局部材料不能证明不存在全局约束。权威来源仍按自身证明力和前提是否成立使用：明确的依赖、分层、跨边界入口或机械检查若前提仍成立，就约束候选结构；前提失效时，不再把对应结论当作当前约束，并把原权威来源的演进纳入战略设计结论。外部项目、文章和通用架构模式只用于比较和挑战，不替代当前 repo 的权威，也不因为外部系统采用某个固定层序就机械套用到当前能力。其他材料各按自己的证明力使用：领域文档说明业务语言和概念；ADR 说明某次重要取舍及当时理由；代码、配置、测试和运行时说明当前现实；修改历史说明哪里以及怎样发生变化；工程摩擦说明当前结构在哪些地方难以理解、切分、修改或验证。它只有在能追溯到责任、依赖、抽象或权威边界时才是架构证据；需求本身过大、测试环境笨重、一次性实现困难都可能只是局部问题。任何一类材料都不能单独代替战略设计。

不要把当前目录树、类关系或已有实现直接抬升成目标结构，也不要因为某份旧架构文档存在就停止判断。已有设计与现实冲突时，检查其前提是否仍成立。

## 怎样形成目标结构

从当前问题覆盖的最小范围开始，不设计整个 repo。用户点名的文件、类或模块只是调查入口；沿真实调用和长期变化找到能拥有这类变化并解释结构摩擦的最小稳定责任范围，以它作为设计中心。先画清主要能力之间的责任、权威和依赖，再判断通用与特化和信息隐藏。若能力内部仍有长期责任、依赖或抽象问题，继续确定内部稳定语义、具体实现的隔离边界和单向依赖，使稳定语义不依赖具体实现。

单向依赖是要保持的结构性质，不等于预设固定层数或层名。只有当前 repo 自己已有仍有效的分层或依赖约束时，才按这些约束检查候选；没有这类权威或稳定内部角色时，不为形式整齐套用外部层序。长期依赖边界仍优先通过目录、模块、包、构建或工具机械约束。运行时调用顺序只说明现实行为，不代替代码依赖设计。

候选结构至少要经得住四个问题：

1. **理解**：理解一个主要能力，是否必须跨很多不相干责任重建知识？
2. **修改**：同类变化是否会穿过本不该参与的模块？
3. **切分**：一个合理范围的业务需求能否主要沿责任边界拆开，而不是按文件或技术层硬切？先排除需求本身范围失控或责任归属未决。
4. **验证**：主要行为能否从对应责任附近获得可靠证据，而不是绕过边界拼装内部细节？先区分架构边界问题与测试基础设施、外部依赖或环境成本。

能力内部存在这类长期结构复杂性时，同样用这四个问题检查内部结构：稳定语义不依赖具体实现，同类变化能在明确边界被吸收；如果 repo 自己已有仍有效的分层或依赖约束，再检查候选是否满足它。

若多个候选都经得住这些问题，再比较它们对后续变化的传播：优先让同类持续或已明确的未来变化少跨责任、权威、依赖和验证面，而不是选择当前改动更大或更整洁的结构。只有边界真实更清楚时这种局部性才成立；不能吞并独立权威或生命周期，也不能复制事实或隐藏真实跨边界语义。

这些问题用于挑战设计，不意味着追求单模块、单测试或最少文件。真实独立的权威、生命周期和领域语义可以合理地跨边界。

## 持久化战略设计

当战略设计形成了跨变化仍会复用的稳定结论，才把它沉淀到 repo 的权威架构来源。内容应短、局部、可修订，只记录责任、边界、依赖、通用/特化、重要不变量和仍未决的结构问题。不要写目录清单、实现步骤、一次性迁移方案或当前代码说明。

已有权威架构来源优先原位更新，不建平行 SOT。repo 没有架构来源时，也不要因为一次 AE run 自动创建全量 `ARCHITECTURE.md`；只有结论已经稳定、未来确实会复用且用户授权时，才建立最小来源。
