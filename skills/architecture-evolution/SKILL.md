# Architecture Evolution · 战略设计与下一步演进

AE 的核心是战略设计：先恢复这个 repo / 系统长期负责什么、当前范围在其中应承担什么角色，再结合领域逻辑、仓库现实、已有设计知识和工程摩擦形成当前最可信的长期结构。下一步演进只是战略设计在当前现实上的战术落地：决定现在值得推进哪一刀，不反过来用当前迁移成本、实现便利或局部压力改写长期目标结构。稳定且未来仍会影响判断的结论，可更新到仓库已有的权威架构来源；文档是战略设计的持久化结果，不是前置答案。用户决定业务、兼容和风险承诺，实现者决定具体代码。

## 流程

**1. 恢复方向并看现实。** 从用户给出的模块、能力或工程摩擦开始，但不能让当前入口或目录边界先验定义 Target Architecture。先恢复足以改变当前战略设计的 repo identity 与 architecture intent：这个系统为什么存在、在更大系统中长期承担什么核心职责、当前范围在整体中预期负责什么、哪些能力或权威明确属于其他 owner。只查与当前范围有关的战略锚点，不做全 repo inventory；任何单一文档、当前模块或现实形态都不能独自定义 identity。

再查当前责任、依赖、权威、生命周期、公开边界，以及理解、修改、需求切分和验证的真实困难。架构文档、领域文档和 ADR 各按其证明力使用；没有破题点时可用近期修改历史找入口，但热点不能直接证明架构问题。只查会改变判断的事实。

**2. 做战略设计。** 先依据当前最可信的 repo identity / architecture intent 与领域语义恢复预期的主要能力划分，再用仓库现实验证和挑战；当前 module / class / package 只是 reality，不能因为已经存在就自动成为长期 capability。随后收敛每项能力应拥有并隐藏的长期知识 / 设计决定、状态、行为、权威、生命周期和主要验证，判断哪些变化应由一个 owner 吸收、哪些差异只是内部 variation、哪些边界由独立语义 / 权威 / 生命周期或会塑造结构的 binding constraint 维持，并明确会改变 Target 的跨边界关系；最后确定稳定依赖、通用/特化和信息隐藏。目标结构不清、范围内仍有长期责任/依赖/抽象未解释，或需要挑战时读 [strategic-design.md](references/strategic-design.md)。

只有长期责任、依赖、抽象或旧权威路径应变化，才升级为架构问题。证据可以是长期变化被结构放大，也可以是现实偏离当前最可信的战略设计，并且这种偏离能追溯到长期责任、依赖、抽象或权威边界，持续造成理解、切分、修改或验证摩擦。单个坏味道、一次性迁移和纯整洁问题都不够。事实先查；业务、兼容和风险取舍交给用户。上游能力调用时只返回证据、方向和人的决策面，不接管提问。

**3. 写方案。** 战略设计先独立回答“长期应该怎样”；现实与目标之间的 gap 只形成候选，不自动成为任务。当前迁移成本、局部实现压力、执行风险和收益只决定现在推进哪个候选、推进到哪里，不把较便宜或较容易的现实形态重新定义成 Target Architecture；已明确的长期变化、binding requirement 或长期风险承诺仍属于战略设计 Evidence。只选择当前最有价值的不超过 3 个改进项。

每项改进都要把一个已确认的战略结论变成更真实的结构：让责任更闭合、边界间更少泄漏私有知识和不必要耦合，在已成立的边界上形成稳定依赖与信息隐藏，并让对应旧知识、旧权威、反向依赖或特殊路径退出。多个候选都符合目标结构时，优先选择能让同类持续或已明确的未来变化少跨责任、权威、依赖和验证面的方向；不能靠吞并已有独立责任、复制权威事实或隐藏真实跨边界语义制造这种局部性。

没有值得立即改变 repo 的内容时，可以只交战略设计结论。未选择的 gap 可以延期、保留或等待更多证据，不为“更接近理想架构”强行推进。只有稳定且未来仍会改变判断的战略设计结论才值得更新到权威架构来源。每项改进都应能追溯到它所实现的战略结构，以及它所回应的真实或已明确的未来压力，或现实偏离目标结构造成的持续工程摩擦；并说明要实现的架构结果、现在优先它的理由、退出的旧知识、权威来源、依赖或路径，以及证明该结果成立的结构事实。研究、未来愿望、纯整洁改动，以及只为后续改造准备条件而自身不产生结构收益和退出的步骤，都不算改进。已有权威架构来源需要演进时更新原处，不建平行规范。

**4. 交付。** 局部问题只给局部判断；缺关键事实或人的决定时，说明缺口与继续条件；收敛后完整给出当前范围的战略设计结论、必要的目标结构变化和当前演进方案，并把同一正文写入仓库或工作区外的 Markdown 交接文件。若获授权，稳定结论更新原权威架构来源；否则交接文件不成为仓库 SOT。不附调研流水、淘汰方案、推理轨迹或旧版本。实质修正后重算并完整重交付；写入失败就是阻塞。不要输出 `ready`、`completed`、`executable` 或 `status` 状态词。

## 判断

- **责任。** 主要能力由 repo identity、领域语义、长期变化和会塑造结构的 binding constraints 共同解释，不由当前目录名决定；同一能力需要的知识、状态、行为、权威、生命周期和主要验证尽量在 owner 内闭合，调用方不重组私有事实。已有独立权威来源或生命周期的相邻系统保持独立，不为内聚而吞并。
- **依赖。** 在责任边界成立后，先明确会改变 Target 的跨边界关系，再保持少量稳定的单向依赖，通用层不依赖具体实现。长期边界优先由目录、模块、包、构建或工具直接约束。反复靠说明解释责任或依赖，是结构未表达清楚的线索；无法由结构推出的业务语义仍应保留说明。
- **差异。** 战略设计先判断差异是否值得成为长期结构：抽象稳定语义，不抽象表面相似。没有长期语义、契约、生命周期、性能架构或部署差异，不制造独立提供者；真实差异也不强行统一。用户点名的分层、门面、提供者或注册表只是候选手段。
- **局部性。** 当前演进应让理解一项责任、完成同类修改和证明其主要行为尽量在同一责任附近闭合。这是找对长期能力与边界并把它物化后的结果，不能为了方便智能体、测试或当前实现而重塑主要责任、复制权威事实或隐藏真实跨边界语义。
- **退出。** 旧知识、旧权威来源、反向依赖、特殊路径、兼容路径，以及只为弥补旧结构歧义存在的说明必须真实退出。新层仍转回旧结构只是搬运复杂度；临时双轨必须有用途和退出条件。

主要责任决定边界；日志、监控和性能等辅助关注点不能反过来塑造主结构。没有性能数据、服务目标或资源证据，不得以性能为由打穿边界。都成立时，选概念更少、公开接口更小的。

文件大、目录乱、分支多、重复多，加一层但旧路径仍在，或只让一次迁移更顺，都不构成优先架构改进。没有当前长期证据，不预留模式、扩展点、钩子或通用框架。

只有用户、仓库或上游权威来源，以及已验证的现实，才能绑定长期承诺或当前事实。AE 可以形成候选战略设计，但不能把它伪装成已有权威。除非某种表示已被权威固定，AE 只规定架构结果和结构完成条件，不提前规定类、接口、文件、配置、调用形态、合并请求、任务拆分或测试工具。

## 发出前检查

1. 是否先恢复了足以约束当前范围的 repo identity / architecture intent 与预期角色，再形成主要能力划分，而不是从当前模块、代码或某份文档直接反推 Target？
2. Strategic Design 是否独立说明长期应有哪些能力、边界、差异与依赖，没有被当前迁移成本、实现便利或局部 pressure 改写？
3. 当前选择的每个改进是否真正物化一项战略结论，并改善责任闭合、耦合、依赖或信息隐藏且产生 real exit？未选择的 gap 是否允许合理延期、保留或等待更多证据？
4. 方案是否停在架构结果，更新或引用原权威来源，并完整交付？
