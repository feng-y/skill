# Execution Compile

Use only after Stable Intent. The goal is one compact taskbook that an Executor can run without ordinary Human orchestration.

## Ground first

Inspect the real workspace and governing surfaces. Run accessible critical commands and capture material baselines. Treat documentation, conventions, and command names as claims until evidenced. Facts unavailable to the compiler become explicit Task 0 checks, not invented state or unnecessary Human questions.

## Taskbook anatomy

Start with a short unheaded opening:

- the taskbook is the execution source; unresolved items go to `BLOCKED.md` while independent work continues;
- after interruption, read `PROGRESS.md` and resume rather than restart;
- one sentence for Why and the completed world;
- priority order when requirements conflict;
- hard rules versus guidance.

Then use six sections.

### 1. Delegated decisions

List each unconfirmed choice the compiler closes: question → default → why reasonable → cost if wrong → detection or rollback. A delegated default may remove ordinary orchestration; it may not change Stable Intent.

### 2. Boundaries

Prefer an allowed write-scope whitelist. Name protected tests, schemas, acceptance scripts, CI, baselines, and other judges. Call out tempting side work and irreversible actions; they are blocked or require Human authority, not silent scope expansion.

### 3. Current state and Task 0

State evidenced facts with source, relevant baselines, and unverified claims.

Task 0 runs before material change. It binds repo/worktree/target, verifies critical commands and judges, detects no-op checks, and writes an opening receipt of Goal, order, largest risk, and disagreement to `PROGRESS.md`. If reality differs:

- revise remaining work when Goal and boundaries still hold;
- park an affected branch while safe work remains;
- block with the exact resolving condition when no safe work remains;
- return to Intent Take when Goal or a confirmed boundary would change.

Reuse fresh evidence applicable to the same execution object; do not repeat discovery ceremonially.

### 4. Task N

Order tasks by real dependency. Each task states:

- one observable result;
- where to begin and why it is ready;
- hard constraints and write ownership;
- verification command or evidence procedure;
- machine-judgable PASS condition;
- reverse validation when failure could be silent;
- evidence invalidated if upstream work changes.

Use a linear order for simple work. Expand a graph only for real independent branches, dependencies, shared writes, joins, or evidence invalidation. Give every shared mutable surface one owner.

### 5. Rules

Include only rules that change execution behavior:

- update `PROGRESS.md` after material checkpoints;
- record blockers, attempts, missing conditions, and safe remaining work in `BLOCKED.md`;
- do not skip tests, weaken assertions, narrow the judged population, mock away the object, swallow failures, edit the judge, or accept a lower baseline unless Stable Intent explicitly requires it;
- every retry changes the hypothesis or approach; stop known-bad routes immediately; three failures against the same acceptance condition in one route force replan, branch switch, rollback, `BLOCK`, or `ESCALATE`;
- roll back unauthorized regression and report failure truthfully;
- follow repository branch, PR, and pre-submit rules.

The Executor owns implementation How and may split, merge, reorder, or park remaining work inside Stable Intent and protected proof. Material replans are recorded in `PROGRESS.md`.

### 6. Completion conditions

Close the result, not the activity. Require:

- evidence for the complete Goal;
- preservation of confirmed boundaries and protected judges;
- actual command output or reproducible evidence, not a completion claim;
- residuals and `BLOCKED.md` contents, including “none” when empty;
- a stop budget or truthful terminal blocker.

Local task PASS is not complete-Goal PASS. Bind independent acceptance when required; otherwise cap the result at `ready for independent acceptance`.

## Fit to run

Keep one taskbook small enough to close as one execution effort. If the Goal cannot be split without losing meaning, keep the whole Goal but compile bounded independently verifiable milestones. Do not let the graph grow without a completion route.

## Research and decision work

Use the same structure, replacing implementation output with a bounded learning goal. Each conclusion needs a source/date or reproducible probe; fabricated citations, unrun “measurements”, and filler findings are failure. A well-evidenced dead end may be a valid result. Stop at the stated budget and deliver the best-supported conclusion plus unresolved alternatives.
