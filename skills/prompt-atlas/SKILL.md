# Prompt Atlas

Perform request-scoped Intent Take. Recover what the user is actually trying to change, ground the context that matters, resolve only decisions that genuinely belong to the user, and leave the next consumer a contract that does not require rediscovering requirement meaning, authority, constraints, or completion criteria.

Compile five minimum semantics internally:

- **Goal Condition** — the desired end state and real problem being solved;
- **Current State** — only current facts, evidence, starting references, and bounded uncertainty that affect the next action or judgment;
- **Boundary** — invariants, acceptable differences, scope, approval limits, protected evaluation or proof rules when material, and any user-owned priority needed to resolve competing constraints;
- **Loop Directive** — what the executor should act toward and how it may organize or revise work from evidence without prescribing a frozen implementation procedure;
- **Evaluation / Stop** — the observable result and evidence that make the Goal met, how an unmet reason feeds the next iteration, or what real blocker prevents safe continuation.

When repo evidence can still change the target architecture, also compile the current **Architecture Intent**. Separate its user-confirmed or governing architecture kernel from its evidence-revisable target model: verified structural facts with provenance, the current target-structure hypothesis, target-shaping unknowns, and the evidence that would refine or reject it. Put only user-confirmed or authoritative governing principles in Constraints; do not harden a general recommendation or inferred design preference into a stable boundary. A final implementation design need not be frozen before work becomes executable when the requested structural outcome, governing kernel, boundaries, and completion condition are stable enough for the executor to refine the design from repo evidence while continuing toward the full requested outcome.

Keep these semantics distinct during reasoning. In Artifact mode, do not collapse a stable result into free-form prose merely for human editability. Compile it into the fixed agent-facing contract below. Structure is part of contract correctness: current frontier-model guidance favors explicit goals, relevant state, constraints, success/evidence requirements, output expectations, and clear separation rather than requiring the next agent to infer those roles from prose. Prompt Atlas adds Decisions to preserve Human authority and makes the goal loop's action, evaluation, feedback, repeat, and stop semantics explicit.

Prompt Atlas owns intent understanding, current Architecture Intent compilation, executable-readiness judgment, and Goal Loop Contract compilation, including explicit Human authority where it materially affects downstream judgment. It does not execute the loop, own runtime state, or provide a durable repo-identity harness. New user authority may revise user-owned intent; territory evidence may revise facts, feasibility, necessary scope, proof state, or current Architecture Intent without silently rewriting the stable intent kernel. Repeated self-refinement on unchanged information is quality review, not new intent. Each invocation terminates after delivering either an Executable Goal Loop Contract or the smallest useful unresolved decision/probe/blocker.

Choose the output mode from the invocation:

- **Artifact mode** — default for explicit `/prompt-atlas` use and direct requests to clarify, consolidate, prepare, hand off, or rewrite a requirement. When safe execution can start, return `Status: Executable` with the fixed Goal Loop Contract and stop. Otherwise return `Status: Unresolved` with only the smallest necessary decision surface, probe, bounded conditional/default, or blocker and stop.
- **Embedded mode** — only when another capability or workflow explicitly invokes Prompt Atlas as an intake sub-capability. Return the compiled intent in the caller's requested carrier or schema and stop Prompt Atlas. Do not infer Embedded mode merely because the ultimate task could later be designed or executed; let the caller own downstream routing unless it asks for a handoff judgment.

Use detailed guidance only when relevant: [contract-anatomy.md](references/contract-anatomy.md) for contract goal attainment and stability, and [completion-trust.md](references/completion-trust.md) for correctness or completion claims.

## Intent Take

### 1. Recover

Recover from the current request, relevant corrections, prior decisions, and examples. When a prior Atlas artifact exists, use still-valid settled semantics as the baseline rather than restarting from raw history. The current user owns intent; current authoritative evidence owns territory. Latest explicit corrections supersede older meaning. Only new user authority may change Goal, user-owned priorities, confirmed decisions, user-owned boundaries, or an explicit requested end state. Better territory evidence may update State, feasibility, proof obligations, current Architecture Intent, or necessary implementation and verification scope without silently rewriting those user-owned semantics. Treat explicit requested outcomes as authoritative until the user supersedes them; do not silently downgrade, defer, split out, or replace one because grounding reveals risk or extra work. Recover desired outcomes separately from suggested means and hard constraints.

Before treating missing detail as an intent gap, judge sufficiency at the resolution level this invocation must establish: outcome, behavior or capability contract, or a user-owned solution commitment. A higher-level artifact is not incomplete merely because downstream design or implementation detail remains open; preserve that freedom unless the detail would change a user-owned outcome, boundary, approval, or proof obligation.

### 2. Ground

Investigate only unknowns whose answers could materially change Goal, Constraints, Loop, Evaluation, Architecture Intent, or whether safe execution can start. Prefer the smallest authoritative check and rich existing references. When territory evidence challenges an explicit user-owned outcome, investigate enough to characterize the conflict and determine whether the outcome can still be satisfied by adding prerequisites, widening necessary scope within current user-owned boundaries and approval limits, or strengthening proof. If satisfying it would cross such a boundary or approval limit, preserve that conflict for Human resolution rather than silently expanding authority. For repo-scoped work, include governing repo-local constraints or acceptance rules when they can materially change Constraints, Evaluation, required evidence, Architecture Intent, or executable readiness; preserve the governing requirement, not a frozen downstream task sequence. Capture a sourced baseline whenever the requested change is judged relative to current behavior or measurement, and keep evidence state and mismatch consequence explicit. Preserve material uncertainty instead of inventing certainty or asking the user for facts the environment can settle. For architecture evolution, ground enough repo reality to distinguish verified architecture facts, the current target-structure hypothesis, and unknowns that can still change owner, boundary, provider, dependency direction, target abstraction, or migration commitment; do not force a final architecture before the evidence supports one. Broader implementation investigation remains downstream unless needed to know what the user means, whether a user-owned outcome is feasible, or whether a safe loop with a measurable Goal can be compiled.

### 3. Resolve human decisions

Resolve only material decisions that available evidence cannot settle and that genuinely belong to the user. If grounding cannot resolve a conflict while preserving an explicit user-owned outcome, surface the conflict with the material evidence, materially distinct options, and one concise recommendation before weakening, deferring, splitting, replacing, or otherwise changing that outcome. If authoritative evidence already proves the outcome infeasible within the settled Constraints and no meaningful user choice remains, return the blocker rather than posing a false question. Do not ask merely because satisfying the same outcome requires more implementation work, broader necessary scope, or stronger verification when those consequences remain inside settled user-owned boundaries and approval limits; absorb them when evidence makes them clear. If a required consequence crosses user-owned scope or approval authority, ask.

Use an ownership test before asking or handing off: a residual choice is Human-owned when two or more evidence-compatible options materially differ in the requested observable outcome, accepted behavioral differences, scope or priority, risk acceptance, or a protected proof rule. If the options differ only in how to satisfy settled intent, leave the choice downstream. If territory evidence can distinguish them, ground first.

As the normal interaction budget, aim for one compact round with no more than five questions. For each question, prefer 2–4 materially distinct options and one concise recommendation with its basis. If that budget would materially reduce goal attainment or stability, exceed it rather than omit a necessary user decision. Do not silently choose a direction or present a recommendation/default as confirmed user intent. A reversible default is allowed only when it leaves Goal and user-owned Constraints unchanged, the cost of being wrong is bounded and reversible, and mismatch is detectable; never use a default to change an explicit requested end state. Mark it visibly as unconfirmed. When a Human decision is required, expose the smallest useful decision surface and stop; do not manufacture another internal round by answering it on the user's behalf.

### 4. Compile and validate

Compile the best current intent when the five internal semantics are stable enough for the next consumer. Before treating the artifact as stable, verify that every explicit user-owned requested outcome is still represented with the same authority or has been explicitly superseded by the user. Omission, silent weakening, deferral, or extraction into a later task is semantic drift. Prefer rich existing references—code, tests, traces, artifacts, schemas, rubrics—over replaying their contents.

For Executable Artifact mode, emit `Status: Executable`, then these canonical headings in this exact order regardless of response language; localize the section contents, not the field names:

1. **Goal** — desired end state. State what should be true when the work succeeds, not merely why the work is useful and not an implementation checklist.
2. **State** — the current baseline, relevant territory facts, evidence and proof state, starting references, completed work if any, and material unknowns. Keep fact, inference, and unknown distinguishable. Do not hide constraints or Human decisions here.
3. **Decisions** — only material choices explicitly confirmed by the user, including approvals that downstream must not reopen. Do not put model recommendations, reversible defaults, guesses, or territory facts here. If there are no additional confirmed decisions beyond the explicit request, state that briefly rather than inventing one.
4. **Constraints** — hard boundaries, invariants, acceptable differences, scope/approval limits, user-owned priorities when needed, and protected oracle/evaluation rules that downstream must not weaken or bypass. Do not turn implementation convenience into a constraint.
5. **Loop** — the operating directive for `Act → Observe → Evaluate → Next`. Name the initial useful direction and require the executor to create or update the minimum task organization needed from current repo reality, execute unblocked work, observe results, and revise the task organization when evidence changes How. Do not freeze a speculative patch sequence.
6. **Evaluation** — the evaluator-visible condition and direct evidence needed to judge the Goal met. Preserve authoritative acceptance paths such as replay/diff. Require each iteration to return `MET` or `UNMET` with a short evidence-based reason; an `UNMET` reason becomes input to the next action rather than a stopping point.
7. **Output** — required downstream deliverable or response format when the user or named consumer specifies one. If no extra output shape is required, require the normal deliverable plus concise final evidence, resulting state, and any true remaining blocker; do not invent unrelated formatting requirements.
8. **Control** — state how to start, repeat, replan, update state, complete, or block. Start immediately from the whole contract; repeat while Evaluation is `UNMET`; complete only on trusted `MET`; block only when no safe next action remains without a new Human-owned decision, permission, authority expansion, or unavailable required external evidence.

Field boundaries are strict: **Goal** is the end state; **State** is current territory and proof reality; **Decisions** records Human authority; **Constraints** defines what cannot drift or be crossed; **Loop** defines how work progresses and dynamically organizes tasks; **Evaluation** judges Goal attainment and feeds the next iteration; **Output** defines delivery shape; **Control** governs repeat and stop.

An Executable Goal Loop Contract must cross one readiness bar: the next consumer can start meaningful work without first obtaining a new Human-owned decision, approval, or authority expansion, and Goal attainment can be judged from an observable end state, a stated check, and the Constraints that must hold on the way there. Ordinary repo investigation, implementation design, local architecture choices, task decomposition, and replanning do not make intent unresolved when the executor can settle them inside the loop.

Task orchestration belongs inside **Loop**, not in a once-frozen plan. For a small task, one dynamic task may be enough. For a larger task, the executor may create tasks with dependencies and local done conditions, execute the first unblocked work, and revise that organization from observations. When State lacks repo detail needed to organize safely, the first loop action may ground and reconcile the plan, but that action cannot become the deliverable or stop the loop.

Apply the exact goal-loop field placement and control semantics in [contract-anatomy.md](references/contract-anatomy.md). For architecture work, use State to preserve the stable architecture kernel, current hypothesis, verified facts and target-shaping unknowns, then let observations revise the design and task organization inside the same loop. Goal and Evaluation must still close every currently requested outcome. Do not reduce a complete requested refactor to one evidence-gathering slice unless the user explicitly made that stage the current end state.

The fixed Artifact-mode structure is a goal loop, not a patch-by-patch taskbook. Do not preselect exact command order, retry counts, executor topology, or a static resource allocation. Preserve the useful Leader semantics—dynamic task organization, current-state updates, ownership of completion, autonomous replanning, evaluator feedback, evidence-based stopping, and honest blocker reporting. If a concrete command or procedure is itself user-owned intent or the authoritative acceptance path, preserve it in the appropriate field.

For repo-changing work, make write scope explicit in **Constraints** when implicit scope is unsafe. Prompt Atlas is done when the next consumer can start the loop without re-deriving Goal, State, Human Decisions, Constraints, the action/evaluation cycle, expected Output, or repeat/stop rules. Downstream work may enrich implementation knowledge and current State, but settled user intent changes only with new user authority. A proof gap cannot become `MET` through rewriting.

When material uncertainty still prevents stable compilation, emit `Status: Unresolved`, expose only the next useful alignment outcome—a focused probe, Human decision surface, bounded conditional/default, or exact blocker—and stop. Do not emit the Executable Goal Loop Contract while user-owned intent or the grounding required for a safe loop and measurable Goal is unresolved. Further convergence requires a later invocation with either new user authority or new authoritative territory evidence. New authority may revise user-owned intent; new evidence may improve grounding and Architecture Intent without changing user-owned intent. Without either new signal, additional self-review may improve consistency or expression but must not promote inference, recommendation, default, or uncertainty into settled intent.

If the user requests a fresh-session handoff, save the same Executable Goal Loop Contract as Markdown in the operating system temporary directory, reference existing artifacts rather than copying them, redact sensitive context, and place any material `Suggested skills` inside **Control**. The saved file is the Artifact-mode outcome and must contain the unchanged `Status: Executable` eight-section contract. Return its absolute path as a delivery-envelope exception rather than emitting a second or altered artifact in chat.

## Output

In Artifact mode, return exactly one of two artifact outcomes: `Status: Executable` with the eight-section Goal Loop Contract above, or `Status: Unresolved` with the smallest result that explains what still prevents safe execution and the next decision, probe, or boundary change that could resolve it. For Executable output, section structure is mandatory even when content is brief. Keep the body dense and avoid explanatory prose outside the selected outcome. Treat brevity as a budget, not a completion gate: never compress away a required authority distinction, material State, constraint, evaluation obligation, loop-control rule, or output requirement. A path-only response is allowed solely as the delivery envelope for a user-requested saved fresh-session artifact; the saved file remains the complete selected outcome. In Embedded mode, honor the caller's carrier/schema while preserving the same intent semantics and authority boundaries. In both modes, delivery ends the Prompt Atlas invocation.
