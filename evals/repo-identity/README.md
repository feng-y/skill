# Repo Identity contract eval

Eval-only. Normal runtime must not read this file.

## Static invariants

Repo Identity passes only when it:

1. acts on the target repository rather than treating the Skill repo itself as the subject;
2. establishes repo thesis, stable capability/responsibility/authority, relevant boundaries/contracts and evidence anchors before calling a local defect the repo's identity;
3. distinguishes semantic evolution pressure from raw file churn;
4. compiles an intent-conditioned repo slice instead of dumping a whole-repo inventory into every task;
5. surfaces improvement opportunities as pressure → identity mismatch → evidence → direction → expected leverage;
6. does not take over Human product Intent, long-term Target Architecture, implementation planning or proof sufficiency;
7. routes factual unknowns to Unknowns First and structural target forks to Architecture Evolution;
8. treats persisted identity as a derived evidence-backed index, not a second authoritative architecture source;
9. revalidates only the identity cone affected by changed evidence anchors instead of rebuilding everything;
10. chooses Human representation according to the judgment need, while diagram/dashboard/interactive artifacts remain disposable projections.
11. distinguishes intentional propagation into derived/index surfaces from duplicated semantic authority before treating co-change as an architecture mismatch.

## Scenario smoke

### RI1 — DaVinci-style broad improvement

A model-serving repository owns request data adaptation, feature semantics, model-input binding and result delivery. The first easy finding is duplicated adapter code. Recent changes also repeatedly touch absence semantics and generation lifecycle across multiple callers.

PASS: identity maps the stable responsibilities/contracts and current evidence first; duplicated adapter code remains only one observation. The improvement map distinguishes local duplication from the broader repeated pressure and can explain whether the higher-leverage issue is authority/contract spread.

FAIL: “deduplicate adapters” becomes the repo improvement target solely because it was easiest to grep.

### RI2 — Small local bug

One parser inside a known owner mishandles one input and the contract/test oracle is already clear.

PASS: do the minimum local repo inspection needed; do not construct a broad Repo Identity, history map or interactive page.

### RI3 — Semantic hotspot, not churn

A generated file changes in hundreds of commits. A stable contract owner changes only a few times, but each change forces synchronized edits in five callers.

PASS: the generated file is not ranked as the meaningful hotspot. The repeated cross-boundary semantic propagation is.

### RI4 — Stale durable identity

An existing identity document says subsystem A owns a contract. Current code/test/config show authority moved to B.

PASS: current evidence wins; mark/replace the stale claim and revalidate affected downstream mappings. Do not preserve both as current truth.

### RI5 — Human projection

A Human asks “why is this repo hard to change?” and the identity model spans several owners, contracts and repeated change paths.

PASS: choose a diagram/timeline/dashboard or interactive artifact when it materially lowers review cost, with evidence links. The generated view is disposable and never becomes the canonical contract.

### RI6 — Intentional derived propagation is not authority duplication

A knowledge repo intentionally requires one source ingest to update the immutable source record, a compiled wiki page, an index entry and an append-only log.

PASS: classify source/wiki/index/log by authority and role first. The synchronized update is not called a structural identity defect merely because four surfaces change together. If the repeated burden is material, surface a narrower lint/derivation automation opportunity while preserving the intended single source authority.

FAIL: raw co-change count is used to recommend merging responsibilities or deleting derived surfaces without showing authority duplication.

## Behavioral claim

These cases establish contract plausibility only. If a change claims that Repo Identity improves agent target formation, repo navigation, review speed, or improvement quality, use `$eval` with real target repos / traces and compare against the baseline behavior.
