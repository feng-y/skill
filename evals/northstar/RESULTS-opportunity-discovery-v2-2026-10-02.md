# Opportunity discovery v2: concrete adoption proposals

## Decision

**Conditionally retain v2 as an unmerged method candidate for review.** In two fixed, matched planning pairs, both candidates produced a concrete capability recommendation and connected Current→Target route; both baselines deferred the concrete change until a future diagnosis of opportunity-selection behavior. This is useful observed planning progress, not demonstrated backend delivery, optimal strategy, realized ROI or general agent reliability.

The candidate chooses an existing maintenance capability to improve, rather than merely choosing a test to discover what might someday need improvement. Independent review found the proposed work current and causally grounded, not an obsolete runner revived or a convenient one-line bug with a value paragraph added afterward. The source remains unmerged; no PR or deployment is authorized or performed.

- Follow important work, recent changes and primary friction through a complete path
- Turn observations, applicable external precedents or explicit causal reasoning into concrete capability proposals
- Challenge them against current implementation, recent fixes, same-outcome existing paths and costs
- Recommend when evidence supports a substantive proposal; preserve genuinely deciding unknowns and valid no-change outcomes
- Connect the adopted proposal to a complete intended state, necessary changes, gradual route and Acceptance in the existing Draft

The main file is 973 UTF-8 bytes shorter than v1, and 442 bytes longer than main; the new conditional reference is 4,928 bytes. These are context-size facts, not measured token savings. Other five runtime Skills and AGENTS are unchanged. No new Skill, Goal, schema, controller, scorer, candidate quota, score formula or separate idea artifact is created. Existing paths compete with new capabilities; reuse is not the default answer. Formation of a reasoned proposal does not require first proving a population-level behavior gain, although claimed effects and promotion still require evidence.

This corrects v1's no-history/no-external-source limitation. It does **not** make a v1→v2 output difference a treatment effect. Only the within-v2 pairs are compared. Historical eval material remains visible in this actual Skill repository; it is not fresh production usage or observed frequency.

There is no short timer, small-patch constraint, mandatory candidate count, section checklist or post-result case selection. All four broad actors and both guards were fixed before the first launch. No coaching or arm-specific answer was sent during these runs.

The paired source difference is only Northstar main plus the new reference: baseline has 152 files including history, candidate 153. ### Iris: identity integrity and complete execution path

Iris statically traced `evals/northstar-beacon-behavioral/run.py` and `judge.py`, then ran an isolated **synthetic backend negative control**. A resumed call requests an old thread ID while the stub returns a different `thread.started` ID. The runner still records the requested ID; the judge package omits that event and repeats the old same-thread claim. This reproduces an instrument gap, not a real model failure or proof that a historical judge accepted an invalid run.

The proposal goes beyond one assignment: identity/termination/final-message eligibility must reach the judge, environment identity must reflect the actual CLI/model/config, and valid continuous sessions must remain distinct from controller-worker's three fresh contexts. It reuses suitable strict parsing/preflight mechanisms already present in the newer runner. First repair the complete continuity claim, then portable binding, then real supported-host acceptance; no general eval platform is proposed.

Independent source review confirms the old runner is still documented for continuous multi-turn cases and imported by the Eval adapter. The newer controller-worker flow does not replace that session shape. Its continued role and distinct semantics make repair a current proposal, not revival of retired work. Independent replay reproduces the synthetic discrepancy.

### Juniper: portable replay plus a refuted expansion

Juniper uses a fake-command/path probe to establish current hardcoded login/model/CLI identity and sandbox arguments without reading real credentials or launching an actor. It compares this with the newer configurable backend, preserves the different session models, and develops a route that also reconstructs already retained Verify authority cases. Historical startup failure is treated as a past host limitation, not proof of a current universal failure.

It also tests an alternative using real loopback RDR: a terminal-started program writes 6,300,000 bytes directly to an ordinary file; after the old client detaches/closes, a new client downloads bytes with the expected hash. That supports an existing known-file path instead of requiring a new spool API for this particular result. It is **not** arbitrary stdout capture, exit-result retention, crash recovery, lack-of-write-permission handling or per-reader cursors. The probe schedules a 0.3-second delay and labels `detached_before_output=true`, but has no event barrier/timestamps independently proving exact ordering; that label is not upgraded into a precise timing claim.

This refutation narrows proposed investment rather than becoming a new mandatory reuse rule. The cost, permission, lifecycle and output constraints remain explicit. No actual backend implementation, portable-host run or measured effort reduction has occurred.

## Evidence, checks and limits

- All six Skills pass the validator; the existing 27 + 11 + 13 instrument regressions pass, independently rerun; `git diff --check` passes. These are instrument/source checks, not 51 agent trials
- Four broad runs and two guards preserve all supplied input bytes at each recorded boundary and final audit. Real shell reads confirm intended source exposure. Cooperative snapshots cannot exclude an unrecorded operation or a within-command edit/revert
- Hazel and Juniper each had an external-provenance serialization/quoting error, then saved the returned source successfully. Those failures remain recorded; they are not product regressions or evidence of an efficiency difference
- Primary external reads are identically permitted, not identical chosen trajectories. Hazel/Juniper used outside sources; Iris/Linden did not need them. No win is assigned for external research volume
- Review is independent and unblinded. No runtime effect, production priority, strategic optimum, sustained execution, automatic routing, implementation transfer, token cost or broad-domain generalization is established by these two pairs

The [compact evidence record](opportunity-discovery-v2-evidence-2026-10-02.json.gz) preserves exact tasks/configuration, source/hash identities, the real history export, full actor-authored plans and probe artifacts, concise action records, external-source provenance and independent review. Unchanged baseline files resolve through the pinned Git commit instead of duplicating historical binary archives.

This public record is deliberately **not a byte-for-byte full tool transcript**. Full original local recorder logs and long external returns were retained for independent audit. Public copies replace third-party article payloads, including copies embedded in shell commands/errors, with arguments, URLs, hashes and omission notes; long repeated source/plan outputs use hashes and retained artifacts. Inherited host instructions and identical non-task reporting suffix are also not exported. Those publication omissions do not rewrite original local evidence or turn missing telemetry into a claim of complete capture.

## Final adoption boundary

V2 has earned conditional retention as a more operational method candidate: concrete proposals and routes appeared in both observed candidate outputs, with the two guards preserved. It has not earned an unrestricted claim that the system now reliably finds the best improvement, nor automatic merge. The branch delivers only the Northstar method and its evaluation; the useful backend proposals remain proposals, not separately authorized implementation work.

Stop this fixed experiment here. Keep v1's negative evidence, v2's actual outputs and the environment/self-repo caveats. Do not append favorable cases, create a scorer or turn the actors' recommendations into an automatic program of extra work.
